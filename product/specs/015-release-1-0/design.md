# 015 — Release 1.0: design

## 1. The route

```
rc.2 (today)
  │  Phase A  CI trustworthy                      R1
  │  Phase B  crash recovery proven               R2
  │  Phase C  API reviewed, Highway's needs, frozen R3, R4
  │  Phase D  numbers published                   R5
  │  Phase E  release gates built and passed      R6
  ▼
rc.3  ── Highway 3.0 RC on it ── staging soak 72 h ── production canary ── 14 days holding up   R7
  │                                   │ a Crystal incident: fix, rc.4, the window restarts
  ▼
1.0.0  = the candidate that held, version changed only                                          R8
```

Phases A and B come first: everything after them measures and ships, and both need a CI that tells the truth and a
store that is proven to recover. Phase C is the last chance for incompatible API changes; D and E prove the candidate.
Crystal does no feature work after rc.3: the production window tests the code that becomes 1.0.

## 2. Phase A — CI (R1)

- **Reproduce locally on Linux**: the machine has WSL with Ubuntu. Run the unit, architecture and process suites in
  a loop there (`--blame-hang-timeout`, trx results kept per run) until the tag run's failure reappears, then
  root-cause it at the interleaving with hooks (playbook § 4), never by retry. The failed run's trx artifact on GitHub
  (needs a login) names the test directly, and is the quicker start if the maintainer downloads it.
- The earlier failed run on `b80b4d0` (1.0.0-preview.1) is read the same way: a second flaky test, or the same one.
- `.github/workflows/build.yml`: pin `runs-on` to `ubuntu-24.04` and `windows-2025`; move `actions/checkout`,
  `actions/setup-dotnet` and `actions/upload-artifact` to versions on the current Node runtime; keep the trx and package
  artifacts. A tag push runs the same jobs as `main`.
- Evidence for R1.2: 20 consecutive full runs per OS, the counts recorded in this spec's tasks.

## 3. Phase B — kill tests (R2)

The crash host (`tests/SystemD.Crystal.CrashHost`, `004` T4) already starts a store in a separate process and is
killed at named steps. Extend it with a **writer mode**: open a database in a given durability mode, commit numbered
batches as fast as it can, and print each batch number the moment its commit returns. The test kills the process after
a random delay, reopens the store, and checks against the printed numbers:

| Mode | What must survive a kill | What may be lost |
|---|---|---|
| Strict | every batch whose commit returned | nothing returned |
| Buffered | every batch older than the last WAL sync before the kill (`SyncInterval`) | at most one interval |
| Relaxed | a prefix of what was committed | any suffix |

In every mode: no batch appears without its predecessors (a prefix, never a hole), and a multi-box batch is whole or
absent. The torn tail: truncate the last WAL file mid-record after a clean stop and reopen. The replicated pair: the
NodeHost process tests (`tests/SystemD.Crystal.NodeHost`) kill the primary mid-load; the standby is promoted, and
every batch the old primary had acknowledged to the standby is on the new primary.

## 4. Phase C — API (R3, R4)

- **Review**: a fresh agent or contributor reads every public type (`dotnet` reflection over `SystemD.Crystal.dll`,
  listed in the baseline below) against playbook § 7; findings are fixed or recorded as kept.
- **Baseline**: `tests/SystemD.Crystal.Architecture.Tests/PublicApi.txt`, one line per public type and member with
  its signature, generated by a test helper and compared by `PublicApi_MatchesTheBaseline`. Updating it is a
  deliberate step, done in the same commit as the API change and its CHANGELOG line.
- **Highway's needs** (`013` R4, R5, R6, R8, R9), each as `013`'s design §§ 5–7, 9, 10 lays it out, with the tests
  `013` names, and the public-API baseline updated with each. No format change (`013` R12).

## 5. Phases D and E — numbers and gates (R5, R6)

- `008` T15 and `013` T1, T2 as written there.
- `tools/release-gate.ps1` (and `.sh`): runs R6.1's list in order with the pool hog on for the concurrency and
  failover tests, stops at the first failure, and appends a dated section to `engineering/measurements.md` with each
  gate's result, the machine, the OS and the commit.
- Highway's gates (R6.2) run in Highway's repository against the candidate's package, from a local feed before
  publishing; their results are recorded here, in this spec's tasks, by commit and package version.

## 6. Phase R7 — production signals

Crystal already emits what production needs on the `SystemD.Crystal` meter and its log events (`007`, `003` § 10).
Highway's dashboards and alerts watch these; the bands below are the pass criteria for the soak and the window, and
the maintainer may tighten them.

| Signal | Instrument | Band |
|---|---|---|
| Strict commit latency | `crystal.commit.duration` p50 / p99 | p50 within 10 % of the soak's; p99 under 15 ms |
| Replication lag | `crystal.replication.lag_time` | p99 under 50 ms; no sustained rise |
| Lost standbys | `crystal.replication.slot_drops`, `slots{state}` | only for a standby deliberately stopped |
| History breaks | `gaps`, `divergences`, `fences`, `epoch_changes` | only during a planned failover or drill |
| Pages from the WAL | `crystal.replication.pull.source{wal}` | near zero outside catch-up |
| Write stalls | `crystal.storage.write.stopped`, `write.delayed_rate` | zero |
| Growth | `crystal.storage.live_data.size`, `sst.size`, process memory | flat after warm-up for steady load |
| Errors | log events at Warning and above | each explained |

A breach is triaged: a Crystal fault is fixed in a new candidate (the window restarts, R7.4); a Highway fault is
Highway's; an environment fault is recorded.

## 7. The cut-over and the rollback (R7.3, R7.5)

Highway 3.0 is a fresh start (protocol 5.0, storage format 4), and on Crystal it refuses a RocksDB-era directory by name
(Highway `076` R3.2). So:

- **Cut-over:** drain the deployment (no queued, in-flight or delayed messages left), stop it, wipe or move its data
  directory, start Highway 3.0 on Crystal, verify with the samples, open traffic.
- **Rollback:** the same in reverse: drain, stop, start the previous Highway on its previous directory (kept, not
  wiped, for the window). Data written on Crystal during the window is not carried back; the runbook says what that
  means for the deployment's queues.

Both are Highway's runbooks; this spec requires that they exist and were rehearsed (R6.2) before R7.3.

## 8. What this design does not do

- No new feature after rc.3: the window tests the code that ships.
- No migration tool: neither direction moves data in place.
- No change to Highway's failover policy: Crystal provides the mechanics; Highway decides.

## 9. Risks

| Risk | Mitigation |
|---|---|
| The Linux failure does not reproduce locally | The trx artifact names the test; read it first. Then loop on Linux under load and with the pool hog |
| A kill test finds a durability defect | That is the point of Phase B; a defect found here is fixed before rc.3 |
| An API change Highway needs is found during the window | Additive: 1.0.x or 1.1. Incompatible: a new candidate before 1.0; the window restarts |
| Production load differs from the harness | The soak runs on the production host class; the window watches the real signals |
| The rollback loses data written on Crystal | Stated in the runbook; the deployment chosen for the canary can tolerate a drain (D5) |
